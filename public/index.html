About this app

This is a working proof-of-concept for embedding per-customer Sigma workbooks via JWT-signed URLs against a single canonical workbook with per-customer version tags. A shared BASE_COLUMNS spec composes with each customer's overlay (extraColumns in CUSTOMER_CONFIG), gets pushed to Sigma as a tagged version of the canonical workbook, and is then embedded via /tag/<tagName>. The customer-specific schema can be driven by a mapping table later — only CUSTOMER_CONFIG needs to change.

The companion to this page is the PRD in docs/prd.md, which captures the full architectural design and rollout plan.

Request flow

Three actors are involved: the browser collects inputs and renders the iframe, an Express server holds the embed secret and signs the JWT, and Sigma validates the token and serves the workbook.

Figure 1 — Embed request lifecycle. The secret only ever lives on the server.
  1. The browser POSTs the embed credentials, embed-user email, selected customer, and Sigma Org Configuration (canonical workbook URL + ID) to /api/embed-url. All values come from the on-page form, persisted via localStorage.
  2. The server resolves the customer's tag (customer-<slug>, or template for the Template target), appends /tag/<tagName> to the canonical workbook URL, signs the JWT, and returns the final URL. No Sigma API calls happen on this hot path — the spec push + tag application were done offline by the sync script (see Figure 2).
  3. The browser sets the iframe src directly to that URL. The server is no longer involved — Sigma validates the token and serves the tagged workbook version to the iframe.

Spec composition (sync flow)

The customer specs live in a static CUSTOMER_CONFIG object in lib/embed.js. The interesting part is the seam: every spec is composed by buildSpec(customer) from a shared base plus a per-customer column list, then pushed to the canonical workbook and tagged. Swap the static object for a database lookup and the rest of the pipeline doesn't change. The diagram below shows the sync flow driven by the two buttons in the Setup tab.

Figure 2 — Sync flow. Base + per-customer overlay → one PUT spec + one tag call → one workbook, N immutable tagged versions.

Embed users never touch separate workbook documents — Customer A and Customer B both see the same canonical workbook, just at different version-tagged URLs. Adding a third customer is a CUSTOMER_CONFIG edit plus one button click.

Why server-side signing?

The JWT is signed with your client secret. That secret must never reach the browser, so /api/embed-url is the only place it lives in memory. The frontend only ever sees the final signed URL. The same secret is also used for OAuth client_credentials against POST /v2/auth/token to drive the Setup-tab sync buttons — both purposes share one credential pair in this POC.

Demo caveat: this POC collects every credential and Sigma config value via on-page form fields so you can try it against any Sigma org without re-deploying. The form values persist in localStorage (with the secret field intentionally not persisted). In production, move the credentials into server-side environment variables and remove the form fields. The canonical workbook ID / URL can stay in the form or move to env — they aren't sensitive.

Customers and tags in this demo

  • Customer A → tag customer-customer-a → adds AGE_GROUP column from Text([Cust Json].AGE_GROUP).
  • Customer B → tag customer-customer-b → adds Birthday column from Text([Cust Json].LOYALTY_EXTRA.BIRTHDAY).
  • Template → tag template → the base columns only (ORDER_NUMBER, SKU_NUMBER, CUST_JSON). The clean starting state operators compare customer overlays against.

Data model assumption

The POC assumes a shared base table with a JSON column (CUST_JSON) that each customer extracts different keys from. The demo's customer overlays are derived fields off that JSON. If your real customers diverge beyond "same base table + different JSON keys" — e.g. distinct source tables, materialized intermediates, or joins — lift the customer-specific logic into a Sigma data model instead of the workbook spec, and tag the data model instead. The PUT /v2/dataModels/{id}/spec endpoint is public and documented; dataModelSourceTaggedVersions on POST /v2/workbooks/tag wires the workbook tag to the data-model tag.

What this POC does not prove yet

  • Performance at production scale, or operational behavior with more than the two customers verified live.
  • Schema drift handling — what happens when BASE_COLUMNS changes in a way an existing customer's extras depend on.
  • Observability beyond the structured operation log shown by the sync buttons.
  • Rollout / version-pinning strategy for spec changes (Sigma's own tag history is the source of truth today; no application-side specVersion field exists).
  • Security hardening beyond the basic JWT pattern — see the demo caveat above.

Setup

One Sigma client credential powers this app — it both signs the embed JWT and authenticates the sync operations that push specs and apply version tags. You'll also need to pick an embed user, whitelist the app's origin in Sigma, and create a canonical workbook to target. All of this gets entered into the on-page form in the Embed tab — nothing is read from a server-side .env file.

1Generate Sigma client credentials

In Sigma, navigate to Administration → Developer Access (depending on your account it may be labelled Embedding).

Click Create New and pick a credential type that covers both purposes — JWT signing for the embed iframe and OAuth client_credentials for the Sigma REST API. Many Sigma orgs allow a single Embed credential to do both. If yours requires separate Embed and REST API credentials, create the one that has the broader scope (typically the REST API credential) and use it everywhere in this app. Sigma will give you:

  • Client ID — a UUID-shaped string. Goes in the Client ID field in the Embed tab.
  • Secret — a long random string. Goes in the Client Secret field. Sigma only shows this once — copy it now.
Docs: Sigma's Generate embed client credentials guide has the canonical walkthrough with screenshots.
Scope it down if you can. The credential needs to sign JWTs and to push specs / apply tags on the canonical workbook (PUT /v2/workbooks/{id}/spec, POST /v2/workbooks/tag). Don't use an org-wide admin token in production.

2Pick an embed user

The JWT's sub claim identifies the user the embed session runs as. Two options:

  • Internal user — an existing user in your Sigma org. Use their email; leave the Account Type and Teams fields blank.
  • Non-Sigma user — any email address. You must also set Account Type (e.g. viewer) and at least one Team so Sigma knows what permissions to grant.

3Whitelist the app's origin

Sigma refuses to render the iframe unless the parent page's origin is on the embed allow-list. In Sigma admin, find Account → Embedding → Allowed embed domains and add:

  • Local dev: http://localhost:3000
  • Deployed: the URL your hosting platform returns (e.g. https://your-app.onrender.com)
Symptom if you forget this: the iframe loads but shows a blank page or a "refused to connect" message. Check the browser console — Sigma surfaces a clear error.

4Create the canonical workbook and fill in Sigma Configuration

Create one workbook in Sigma that will become the target of every version tag. Make sure it has the same structure BASE_COLUMNS in lib/embed.js expects: one page, one table element, the three shared columns (ORDER_NUMBER, SKU_NUMBER, CUST_JSON) sourced from PLUGS_ELECTRONICS_HANDS_ON_LAB_DATA (or your equivalent warehouse table — update BASE_SOURCE in lib/embed.js if so).

Copy the workbook URL and ID into the Sigma Configuration panel in the Embed tab:

  • API Base — your Sigma host's API base, e.g. https://aws-api.sigmacomputing.com.
  • Client ID / Client Secret — from step 1.
  • Canonical Workbook ID — the UUID. Get it from GET /v2/workbooks or from the workbook URL.
  • Canonical Workbook URL — the full browser URL, e.g. https://<org>.sigmacomputing.io/<slug>/workbook/Embed-<id>.

These values are saved to localStorage so you don't retype them every refresh. The secret field is intentionally not persisted.

To customize what each customer sees, edit CUSTOMER_CONFIG in lib/embed.js:

  • Base columns live in BASE_COLUMNS.
  • Per-customer extras live in CUSTOMER_CONFIG.<name>.extraColumns.
  • Each customer's tag name can be set explicitly with CUSTOMER_CONFIG.<name>.tagName, or omitted to use the default slug (e.g. customer-acme-co for "Acme Co").

5Sync customer version tags

With the canonical workbook in place and Sigma Configuration filled in, the buttons below drive the entire reconciliation — spec push + tag application — without anyone having to click around in the Sigma UI. See docs/prd.md for the full architectural design.

  • Sync customer tags from config — for every entry in CUSTOMER_CONFIG, push the composed spec (BASE_COLUMNS + that customer's extraColumns) to the canonical workbook and apply the customer-<slug> tag.
  • Propagate template updates — push the base-only spec, tag it template, then re-sync every customer tag so they inherit the new shared base.
What runs underneath: the buttons POST to /api/sync-tags and /api/propagate-template. Both routes use the same code path as scripts/sync-customer-tags.js, which you can drop into any project that mirrors this CUSTOMER_CONFIG shape. The equivalent CLI invocations:
npm run sync-tags · npm run propagate-template · node scripts/sync-customer-tags.js --customer "Customer A"

One open assumption to know about. The Sigma public REST API documents PUT /v2/dataModels/{id}/spec for data models, but does not document an equivalent path for workbooks. This script assumes the analogous path (PUT /v2/workbooks/{workbookId}/spec) exists. If your Sigma org exposes spec push at a different path, set SIGMA_SPEC_ENDPOINT_PATH and SIGMA_SPEC_ENDPOINT_METHOD in the server's environment. The tag application step uses POST /v2/workbooks/tag, which is public and confirmed.

6Run it

From the project root:

npm install
npm test  (optional, runs the smoke tests)
npm start

Open http://localhost:3000. Fill in Sigma Configuration, pick a customer (Customer A, Customer B, or Template), and click Generate Embed.

Equivalent CLI invocations for the sync operations (CI-friendly, reads SIGMA_* env vars):

  • npm run sync-tags — sync all customer tags from config.
  • npm run propagate-template — push the base spec to template, then re-sync every customer tag.
  • node scripts/sync-customer-tags.js --customer "Customer A" --dry-run — single-customer dry run.
For production: move SIGMA_CLIENT_ID and SIGMA_CLIENT_SECRET into server-side environment variables, and remove the form's Client ID / Client Secret fields. The canonical workbook ID and URL can stay in the form (they aren't sensitive) or move to env. Either way, the signing endpoint and the sync handlers should be the only places the secret ever appears.
