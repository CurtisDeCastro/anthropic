About this app

This is a proof-of-concept for embedding per-customer Sigma workbooks using JWT-signed URLs. It demonstrates a small but useful pattern: a shared base spec that composes additional columns per customer at request time, so the customer-specific schema can eventually be driven by a mapping table rather than hand-maintained workbooks.

Request flow

Three actors are involved: the browser collects inputs and renders the iframe, an Express server holds the embed secret and signs the JWT, and Sigma validates the token and serves the workbook.

Figure 1 — Embed request lifecycle. The secret only ever lives on the server.
  1. The browser POSTs the embed credentials, embed-user email, and selected customer to /api/embed-url.
  2. The server looks up the customer's workbook URL, composes the spec, signs a JWT with the embed secret, and returns the final URL.
  3. The browser sets the iframe src directly to that URL. The server is no longer involved — Sigma validates the token and serves the workbook to the iframe.

Spec composition

Today the two specs are checked into server.js as a static CUSTOMER_CONFIG object. The interesting part is the seam: every spec is composed at request time from a shared base plus a per-customer column list. Swap the static object for a database lookup and the rest of the pipeline doesn't change.

Figure 2 — Spec composition. Base columns are defined once; per-customer columns are merged in at request time.

The shape buildSpec() returns mirrors what the Sigma GET /workbooks/:id endpoint produces — but only pages and layout matter when pushing back into Sigma. Read-only metadata fields like workbookId, ownerId, and timestamps are stripped server-side and aren't part of the create/update payload.

Why server-side signing?

The JWT is signed with your embed secret. That secret must never reach the browser, so /api/embed-url is the only place it lives in memory. The frontend only ever sees the final signed URL.

Demo caveat: this POC collects the client ID and secret from a form so you can try it without re-deploying. In production, store them as server-side environment variables (e.g. SIGMA_CLIENT_ID, SIGMA_SECRET) and remove the form fields entirely.

File map

  • server.js — Express server. Holds CUSTOMER_CONFIG, buildSpec(), and the JWT signing logic.
  • public/index.html — single-page UI. Form, customer selector, live spec preview, and the embed iframe.
  • package.json — runtime deps: express, jsonwebtoken, uuid.

Setup

You need three things from your Sigma org to run this app: an embed client ID, an embed secret, and an embed user email. The deployed app's URL also needs to be added to Sigma's allowed embed domains list.

1Generate embed client credentials

In Sigma, navigate to Administration → Developer Access (depending on your account it may be labelled Embedding).

Click Create New, choose Embed as the credential type, and give it a name. Sigma will generate two values:

  • Client ID — a UUID-shaped string. Goes in the Embed Client ID form field.
  • Secret — a long random string. Goes in the Embed Secret field. Sigma only shows this once — copy it now.
Docs: Sigma's Generate embed client credentials guide has the canonical walkthrough with screenshots.

2Pick an embed user

The JWT's sub claim identifies the user the embed session runs as. Two options:

  • Internal user — an existing user in your Sigma org. Use their email; leave the Account Type and Teams fields blank.
  • Non-Sigma user — any email address. You must also set Account Type (e.g. viewer) and at least one Team so Sigma knows what permissions to grant.

3Whitelist the app's origin

Sigma refuses to render the iframe unless the parent page's origin is on the embed allow-list. In Sigma admin, find Account → Embedding → Allowed embed domains and add:

  • Local dev: http://localhost:3000
  • Deployed: the URL your hosting platform returns (e.g. https://your-app.onrender.com)
Symptom if you forget this: the iframe loads but shows a blank page or a "refused to connect" message. Check the browser console — Sigma surfaces a clear error.

4Wire up your own workbooks (optional)

Out of the box this POC points at two demo workbooks (Customer A, Customer B) in the test-drive-staging-oai-demo org. To use your own, edit server.js and replace the two workbookUrl values inside CUSTOMER_CONFIG.

The URL format Sigma's JWT embed accepts:

https://<sigma-host>/<org-slug>/workbook/<workbook-name>-<workbook-id>

You can also adjust the columns each customer sees — base columns live in BASE_COLUMNS, per-customer extras live in CUSTOMER_CONFIG.<name>.extraColumns.

5Sync customer version tags

The production architecture (see docs/prd.md) collapses the two demo workbooks into a single canonical workbook with per-customer version tags. The buttons below drive that reconciliation without anyone having to click around in the Sigma UI.

  • Sync customer tags from config — for every entry in CUSTOMER_CONFIG, push the composed spec (BASE_COLUMNS + that customer's extraColumns) to the canonical workbook and apply the customer-<slug> tag.
  • Propagate template updates — push the base-only spec, tag it template, then re-sync every customer tag so they inherit the new shared base.
What runs underneath: the buttons POST to /api/sync-tags and /api/propagate-template. Both routes use the same code path as scripts/sync-customer-tags.js, which you can drop into any project that mirrors this CUSTOMER_CONFIG shape. The equivalent CLI invocations:
npm run sync-tags · npm run propagate-template · node scripts/sync-customer-tags.js --customer "Customer A"

One open assumption to know about. The Sigma public REST API documents PUT /v2/dataModels/{id}/spec for data models, but does not document an equivalent path for workbooks. This script assumes the analogous path (PUT /v2/workbooks/{workbookId}/spec) exists. If your Sigma org exposes spec push at a different path, set SIGMA_SPEC_ENDPOINT_PATH and SIGMA_SPEC_ENDPOINT_METHOD in the server's environment. The tag application step uses POST /v2/workbooks/tag, which is public and confirmed.

6Run it

From the project root:

npm install
npm start

Open http://localhost:3000, paste your credentials and embed-user email, pick a customer, and click Generate Embed.

For production: move SIGMA_CLIENT_ID and SIGMA_SECRET into environment variables and remove the form fields. The signing endpoint should be the only place the secret appears.
